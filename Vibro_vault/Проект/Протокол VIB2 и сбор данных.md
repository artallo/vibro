# Протокол VIB2 и сбор данных

Проверено по коду `main.py` 21.09.2026.

## Пакет

```text
MAGIC   = b"VIB2"
header  = "<HHII", 12 байт: N, зарезервировано, elapsed_us, sequence
payload = N × 12 байт
N       = 1024 отсчёта
```

В полезной нагрузке идут подряд N значений X, затем N значений Y, затем
N значений Z, каждое int32. Перевод в g: делением на 256000.

Частота дискретизации не берётся из настройки, а измеряется по каждому
пакету:

```python
fs = (N - 1) / elapsed * 1e6
```

Для сессии берётся среднее fs её пакетов. Поэтому в отчётах при ODR 250
стоит 252,75–252,77 Гц, а не ровно 250.

Поле `sequence` из заголовка читается, но в файл не сохраняется. Из-за
этого нельзя доказать, что ни один пакет не потерян, см.
[[Открытые задачи]].

## Смена ODR

Python отправляет в ESP32 два байта: команду и параметр.

```text
SetODR = 0x01

250 Гц  → 0x00
125 Гц  → 0x01
62.5 Гц → 0x02
```

Подтверждения от прошивки нет.

## Порядок запуска

Этот порядок важен, менять его без причины не нужно:

```text
открыть порт
→ отправить SetODR
→ flush
→ для одиночного запуска дождаться ENTER
→ reset_input_buffer()
→ читать пакеты
```

При `--repeat N` порт открывается один раз, ODR задаётся один раз, а
буфер сбрасывается перед каждым прогоном. Ожидание ENTER остаётся только
для одиночного запуска.

## Разрешение по частоте

При длине отрезка Велча 1024 отсчёта:

| ODR | Ширина бина |
|---|---|
| 250 Гц | 0,244 Гц |
| 125 Гц | 0,122 Гц |
| 62,5 Гц | 0,061 Гц |

Отсюда важное методическое следствие: в экспериментах с разным ODR нельзя
отделить влияние самого ODR от разрешения по частоте и от длительности
записи, потому что N и длина отрезка Велча зафиксированы. Понижение ODR
одновременно улучшает разрешение и удлиняет пакет, сессию и прогон. См.
[[История экспериментов до 09.2026]].

Для текущего анализа длина отрезка задаётся отдельно, см.
[[Разрешение nperseg]].
